# Шаблон проекта

**Людям — начинать с [`kb/docs/README.md`](kb/docs/README.md).** Файлы заполняет агент через скиллы, руками шаблоны не заполняют.

Универсальная структура для любого продукта, который делает пул с ИИ-агентами.
Это git-репозиторий целиком: агента (OpenCode, Claude Code, Claude desktop) запускают из его корня.
Новый продукт — новый репозиторий из этого шаблона, без папки `kb/game/` (порядок — `kb/docs/setup.md`). Продуктовое содержание появляется по ходу работы.
Игра для обучения пула — `kb/game/README.md`. Симуляция «Неделя в репозитории» и ответы ведущего игры — в отдельном репозитории `ai-pool-kb`.

## Что где лежит

Всё о процессе и знаниях — в одной папке `kb/`. Код продукта — где удобно команде: рядом с `kb/` в этом репозитории или в отдельных репозиториях. Где он лежит, записано в `kb/core/context-map.md`, раздел «Где лежит код».

```
AGENTS.md                Правила для агента — общие для Claude Code и OpenCode
CLAUDE.md                Подключает AGENTS.md для Claude Code
README.md                Этот файл
.claude/skills/          Скиллы агентов: Claude Code и OpenCode читают их отсюда, вызов — /<имя>
.opencode/               Агент и команды /kb-… для OpenCode
opencode.json            Настройки OpenCode: агент kb по умолчанию, разрешения, сжатие контекста
.gitlab-ci.yml           CI для GitLab: проверка, номера и сводки после каждого push в context
.github/workflows/kb.yml То же для GitHub Actions

kb/                      База знаний продукта
  product.md             Рутовый эпик: цель, боль, метрика, критерии приёмки
  team.md                Кто есть кто: имя, почта git, роли, стиль общения, режим, архитектор недели, дежурный
  FEEDBACK.md            Замечания к скиллам и правилам
  inbox/                 Сюда кладут новые материалы как есть; kb.py convert делает текст в inbox/_md/
  materials/             Материалы бизнеса: скрипты, файлы, регламенты, ответы; meetings/ — встречи с саммари
  context/               Знание о процессе бизнеса — «как есть сейчас»
    glossary.md          Единый язык: термины и их значения
    process/             Карта процессов: один файл на шаг = один рут; _map.md, _index.md, _map.html
      cards/             Карточки шага: части рута для параллельного разбора
    systems/             Карта систем: один файл на внешнюю систему
  core/                  Ядро: доменная модель, карта модулей, сквозные соглашения
  journal/               Вопросы, допущения, решения, риски, дайджесты; _index.md — сводка
  datasets/              Золотой датасет: реальные случаи с ожидаемым результатом
  specs/                 Спеки декомпозитов, по ним агент пишет код
  docs/                  Инструкции для людей
  tools/kb.py            Проверка, сводки, номера, карта, команды записи; tools/tests — тесты
  game/                  Материалы игры для обучения пула (в продукте удалить)
```

Пути в файлах базы знаний и в выводе `kb.py` — от корня репозитория: `kb/materials/brief/zapros.md`, строка 3. Старые ссылки без `kb/` (`materials/…`) `kb.py` тоже понимает.

## Иерархия работы

| Уровень | Где живёт | Статусы |
|---|---|---|
| Рутовый эпик | `kb/product.md` | — |
| Рут = шаг карты процессов | `kb/context/process/PM-XX-*.md` | Черновик → Готов к взятию → Разбор → Сверка с бизнесом → Нарезка → Приёмка → Декомпозиты в работе → Готово. Кто ставит каждый — `AGENTS.md`, «Статусы рута». Руты не назначают — разработчики берут сами: `kb.py take` |
| Карточка разбора (по желанию, для большого шага) | `kb/context/process/cards/PM-XX-KNN-*.md` | Открыта → В работе → На приёмке → Принята; находки переносит в шаг владелец рута |
| Декомпозит | `kb/specs/PM-XX/PM-XX-NN-*/` | Опции → Спека → Ревью спеки → Сборка → Приёмка → Канарейка → Готово |
| Задача агента | `plan.md` внутри декомпозита | На доску не выносится |

Общие части, нужные нескольким рутам, живут в отдельном руте `PM-00 Каркас и общие части`, его содержание — папка `kb/core/`. Ведёт техлид потока (нет — архитектор недели).

## Идентификаторы

| Объект | Формат | Пример |
|---|---|---|
| Рут (шаг процесса) | `PM-XX` | `PM-04` |
| Декомпозит | `PM-XX-NN` | `PM-04-02` |
| Система | `SYS-XX` | `SYS-01` |
| Вопрос | `Q-NNN` | `Q-014` |
| Допущение | `A-NNN` | `A-007` |
| Решение | `D-NNN` | `D-005` |
| Риск | `R-NNN` | `R-003` |
| Карточка шага | `PM-XX-KNN` | `PM-04-K02` |
| Случай датасета | `GD-PM-XX-NNN` | `GD-PM-04-017` |

ID никогда не переиспользуется. Ссылки между файлами — только по ID.
Вопросы, допущения, решения и риски создаются с временным ID `Q-new-<имя>`, постоянный номер присваивает CI после каждого push в `context` (см. `kb/tools/README.md`).

## Три правила, на которых держится всё остальное

1. У каждого факта есть источник и статус: `(источник, подтверждено | оценка | допущение A-NNN | противоречие)`.
2. Ответ существует, только если он записан коммитом. Коммит с ответом содержит ID вопроса или допущения.
3. Один файл — один писатель. Файлы создаёт `kb.py new …` по шаблонам `_template`; структуру меняет аналитик, содержание — весь пул. Кто что пишет — `AGENTS.md`. Все работают в ветке `context`, отправляет агент (`kb.py push`) — `kb/docs/git.md`.
