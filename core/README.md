# Ядро проекта

Ядро — то, на чём стоят все руты: модель предметной области, границы модулей и сервисов, сквозные соглашения. Это содержание рута `PM-00 Каркас и общие части`.

## Зачем отдельно

Если общие вещи живут внутри рутов, каждый владелец рута придумает свою версию главного объекта, и через месяц в системе будут несовместимые модели. Всё, что нужно больше чем одному руту, принадлежит ядру.

## Что входит

| Файл | Что описывает | Кто ведёт |
|---|---|---|
| `domain-model.md` | Сущности, жизненный цикл главного объекта, источники правды | Архитектор недели, наполняют владельцы рутов |
| `context-map.md` | Модули и сервисы, чем владеют, какие события публикуют, базы данных | Архитектор недели, техлиды потока |
| `conventions.md` | Идентификаторы, деньги, время, ошибки, логирование, тоглы, миграции | Техлиды потока |

## Как ядро меняется

1. Первая версия — после сессии по событиям в конце разбора карты процессов.
2. Дальше ядро меняется только через спеки: в каждой спеке есть раздел «Изменения модели».
3. Архитектор недели на ревью спеки сверяет этот раздел с ядром.
4. После приёмки декомпозита изменения вливаются сюда тем же коммитом или следующим.
5. Изменение, которое трудно откатить, сначала оформляется решением в `journal/decisions/`.

## Что решаем заранее, а что откладываем

| Решаем до первого декомпозита | Откладываем до спеки декомпозита |
|---|---|
| Главный объект, его ключ и жизненный цикл | Поля сущностей сверх ключевых |
| Источник правды для каждого вида данных | Конкретные форматы файлов и сообщений |
| Границы с внешними системами | Детали каждой интеграции |
| Разрез на сервисы, одна база на сервис | Экраны и отчёты |
| Где хранятся персональные данные | Оптимизации под нагрузку |
| Правила денежных операций и идемпотентности | |
