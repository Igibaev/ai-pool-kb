# Карта процессов

Инструкция для людей с примерами — `docs/process-map.md`; всё нужное агенту — ниже.

Карту ведёт аналитик. Если `git config user.name` не аналитик — не меняй структуру: предложи правку через вопрос `kb-ask` с типом «скоуп».

## Режим 1. Черновик с нуля

### 1. Подготовка
1. `git pull --rebase`, если есть remote. Прочитай `product.md` и материалы: маленькие целиком; большие — `<имя>.summary.md` или `python3 tools/kb.py peek <файл>`.
2. Карт столько, сколько у продукта главных объектов с независимым жизненным циклом. Почти всегда одна. Две карты — только если объект может жить без первого процесса. Сомневаешься — одна карта, вопрос человеку.

### 1а. Новый продукт без текущего процесса
Если продукта ещё нет и бизнес-процесса тоже (идея), карта всё равно строится **по тому, как пользователи решают задачу сейчас**: руками, в Excel, в мессенджере, у конкурента. Это материал из интервью `kb-init`.
Если сейчас задачу не решают никак — карта описывает задуманный путь главного объекта. Тогда шаги, которых пока нет в жизни, помечай в «Зачем этот шаг бизнесу»: «Шага сейчас нет: так задумано (интервью …, подтверждено как решение владельца)». Цифры по ним — оценки.

### 2. Найти главный объект
Задай себе и человеку три вопроса:
- Что движется по процессу от начала до конца? (надпись, заявка, договор, заказ)
- Какое событие его рождает?
- Какими событиями путь заканчивается? Обычно их несколько: успех, отказ, отмена.

Ответ — с источником. Нет источника — вопрос человеку прямо сейчас, без него карту не строим.

### 3. Найти шаги
1. Выпиши состояния главного объекта по материалам: что с ним происходит, в каком порядке.
2. Шаг = переход объекта из одного состояния в другое. Название — действие + объект: «Регистрация надписей», «Сопоставление оплат». Не отдел («Бухгалтерия»), не система («1С»), не «Обработка» или «Работа с …».
3. Проверь каждый шаг:
   - у шага есть вход и выход, и выход отличается от входа;
   - шаг делает одна группа людей или одна система;
   - шаг можно описать на одной странице;
   - внутри шага нет своего маршрута с развилками на несколько дней — иначе дели.
4. Цель — 5–12 шагов. Меньше пяти — шаги слишком крупные. Больше двенадцати — вы описываете действия, а не шаги.
5. Параллельные ветки — отдельные шаги, не продолжение цепочки. Пример: оплата может прийти в любой момент после регистрации надписи.
6. Исключения (отказ, возврат, отмена) — пунктир на схеме, а не отдельные шаги, пока внутри них нет своей работы.

### 4. Оформить
1. Сначала `context/process/_map.md`: главный объект, схема mermaid, таблица «Шаги», черновой жизненный цикл. По схеме `kb.py` рисует картинку, поэтому пиши её так:
   - шаг — узел с меткой «ID название»: `PM04["PM-04 Сопоставление оплат"]`;
   - конец пути — круглый узел: `X1(("Закрыта"))`;
   - основной путь — `-->`, ветки и исключения — пунктир с подписью: `PM01 -. оплата в любой момент .-> PM04`;
   - каждый шаг из таблицы есть на схеме, кроме PM-00.
2. Файл шага — командой, не копированием шаблона: `python3 tools/kb.py new step <slug> шаг="<Действие + объект>" "порядок=N из M" системы=[SYS-01] "Зачем этот шаг бизнесу=<1–2 фразы> (источник, статус)"`. Номер — следующий свободный по порядку основного пути; `PM-00` уже есть. Главный объект команда возьмёт из `_map.md`. Черновые «Вход и выход» допиши точечно с пометкой «черновик аналитика». Остальное наполнит владелец скиллом `kb-explore`. После каждого `new step` — строка в таблицу «Шаги» и узел на схеме; `python3 tools/kb.py check` сверит.
3. Системы: `python3 tools/kb.py new system <slug> система="<название>" "Роль в процессе=<…> (источник, статус)"` на каждую внешнюю систему.
4. Глоссарий: термины, которые встретились в материалах, с источником. Если бизнес называет одно и то же по-разному — один термин, синонимы в колонке.
5. В `product.md` в «Дереве метрики» замени названия шагов на ID.
6. `python3 tools/kb.py index` — посмотреть сводки и карту: `_map.svg` и `_map.html` (интерактивная: статусы, владельцы, вопросы, декомпозиты по клику). В коммит эти файлы не добавляй — их коммитит CI. `python3 tools/kb.py check` предупредит, если шаг есть в файлах, но не на схеме.

### 5. Подготовить сверку структуры с бизнесом
Сделай для человека список вопросов на 30–40 минут встречи:
- «Вот шаги по порядку — так вы работаете? Чего не хватает?»
- По каждому шагу: кто его делает, в чём, сколько раз в день или неделю.
- Где начинается и где заканчивается процесс для вас?
- Что идёт параллельно, а что строго по очереди?
- Где больше всего ручной работы и ошибок?
Бизнес проверяет структуру, а не содержание шагов. На встрече показывайте `context/process/_map.html` — схему, а не таблицу. Итоги — режим 2; только после сверки структуры — режим 3.

## Режим 2. Изменить структуру

Основание — ответ бизнеса или вопрос типа «скоуп». Каждое изменение — строка в «Изменения структуры» в `_map.md`: дата, что, почему, вопрос.

| Что | Как |
|---|---|
| Добавить шаг | `kb.py new step` — следующий свободный номер, даже если шаг встаёт в середину. Обнови `порядок` у всех шагов, строку в «Шаги» и схему |
| Разделить шаг | Старый ID остаётся у первой части. Вторая часть — `new step` с новым номером |
| Объединить шаги | Остаётся меньший ID. `python3 tools/kb.py refs PM-YY` — все упоминания перенеси на оставшийся. Файл PM-YY удали. Номер PM-YY больше не используется. Если у шага уже есть декомпозиты — не объединяй, вопрос архитектору недели |
| Переименовать | Меняется название, ID остаётся |

ID никогда не переиспользуется.

### Разделить или объединить взятый рут
Повод — вопрос «скоуп» от владельца (разбор показал, что внутри два шага или два шага — один).
1. **Разделить.** Аналитик создаёт `PM-YY` командой `new step` и правит карту. Владелец переносит факты в `PM-YY` MR-ом (или аналитик, если владелец согласен). По вопросам новой части — `python3 tools/kb.py set Q-… раздел=PM-YY`. Затем `PM-YY` — в «Готов к взятию» (режим 3): его берут отдельно, в том числе тот же владелец, если лимит позволяет.
2. **Объединить.** Остаётся меньший ID и его владелец. Владелец второго становится напарником (`людей: 2`, `take`) или отпускает (`release`). Факты второго переносит его владелец MR-ом в оставшийся файл, вопросы — `set Q-… раздел=PM-XX`.

## Режим 3. Подготовить шаги к взятию

Когда: структура сверена с бизнесом. Цель — разработчик открывает шаг и за 10 минут понимает, о чём он и с чего начать разбор. Руты не назначают: разработчики берут их сами (`/kb-take`). Аналитик **не разбирает шаг** — это работа владельца.

Для каждого шага:
1. «Зачем этот шаг бизнесу» — 1–2 фразы с источником.
2. «Вход и выход» — уточнить по итогам сверки.
3. «Участники» — роли бизнеса на шаге и что они делают.
4. «Боль» — только то, что бизнес сам назвал болью, с источником. Не называл — пусто.
5. «Материалы и контакты» — материалы по шагу, по строке на файл: `- materials/… — что в нём по этому шагу`; и «Кто отвечает в бизнесе: <роль>» — только роль; через кого ходить — таблица в `team.md`, источник правды по контактам. Нет ни одного материала — шаг не готов: сначала созвон с бизнесом (`/kb-interview`) или запрос материалов.
6. `системы` в шапке — какие системы участвуют в шаге, по брифу и материалам. По ним разработчик, взявший рут, решит, брать ли и систему.
7. `приоритет` в шапке — вместе с менеджером: 1 — брать первым. Выше те шаги, где боль больше и от которых зависят другие.
8. `людей` в шапке — 1 или 2. `python3 tools/kb.py ready-check PM-XX` даёт **только подсказку** по четырём признакам: систем в шапке, скриптов и выгрузок в «Материалах», ролей бизнеса в «Участниках», связей на карте. Решает аналитик. Больше двух не ставь: третий начинает делать за других, и каждый надеется на соседа. Подсказка говорит «много даже для двоих» — раздели шаг (режим 2).
9. `python3 tools/kb.py ready-check PM-XX` — что ещё не готово. Готово — `python3 tools/kb.py set PM-XX статус="Готов к взятию"`.

**Где остановиться.** 30–60 минут на шаг. Аналитик не пишет «Как сейчас», «Правила», «Исключения», «Объём и время», «Идентификаторы», «Данные» — их владелец добывает из материалов сам. Знаешь факт из интервью — не держи в голове: заметки интервью в «Материалах», а факт добудет владелец. Тянет писать дальше — это признак, что начался разбор: остановись.

## Проверка и отправка

Отправка — по таблице «Режим работы» в `AGENTS.md`: карта и шаги — MR; `team.md` и объекты журнала — прямой коммит.

1. `python3 tools/kb.py check`.
2. Коммит: `git commit -m "Черновик карты процессов: 7 шагов, 3 системы" -m "Скилл: kb-map" -- <файлы>` или `… -m "Карта: PM-05 разделён на PM-05 и PM-09 (Q-…)" …`. Сгенерированные `_index.md`, `_map.svg`, `_map.html` не добавляй.

## Скажи человеку
- Главный объект, сколько шагов, какие ветки и исключения.
- Какие места карты основаны на догадке и требуют сверки — это вопросы на встречу с бизнесом.
- Следующий шаг: сверка структуры с бизнесом, затем подготовка шагов к взятию (режим 3). Руты разработчики берут сами: `/kb-take`.
