# Правила для агента

Репозиторий — база знаний и код одного продукта. Его ведёт пул людей с агентами одновременно. Кто есть кто, режим работы, архитектор недели и дежурный по знаниям — `team.md`. Скиллы — `/kb-…`; не знаешь, с чего начать, — `kb-next`. Документы в `docs/` написаны для людей: всё нужное агенту есть в скиллах.

## Всегда

1. Кто работает: `git config user.name` → роль в `team.md`. Имени нет — скажи и попроси добавить.
2. Перед работой — `git pull --rebase`, если есть remote (`git remote` пусто — пропусти pull и push).
3. Факт — только из материала или ответа: `текст (источник, статус)`. Источник — путь и место: строка, функция, лист. Статус: `подтверждено`, `оценка`, `допущение A-…`, `противоречие`. Слова участника процесса о своей работе, даже диапазоном («3–4 часа»), — `подтверждено`; «примерно», «наверное», «думаю» — `оценка`. **Противоречие** — два источника по-разному описывают одно и то же, в том числе внутри одного шага: скрипт делает так, а люди руками — иначе. Не выбирай сам: запиши оба факта со своими источниками и статусом `противоречие` и заведи вопрос — тип «бизнес-правило», если выбирает бизнес, «решение» — если пул. Из опыта — вопрос, не факт. Роли, а не имена людей; объёмы и время — числами.
4. Один файл — один писатель.

   | Файл | Кто пишет | Остальные |
   |---|---|---|
   | Шаг `PM-XX` | Владелец рута. Напарник (`людей: 2`) — в своих разделах; статус и нарезку ведёт владелец | MR владельцу или вопрос. Исключение: архитектор недели дописывает «Приёмка рута» и меняет статус на приёмке (`kb-accept`) |
   | `PM-00`, `core/` | Техлид потока; нет его — архитектор недели. Берётся `kb.py take PM-00` | Вопрос «скоуп» с разделом `PM-00`; изменения ядра — через спеку декомпозита |
   | Система `SYS-XX` | Владелец раздела | MR владельцу или вопрос |
   | `_map.md`, `product.md`, `team.md` | Аналитик | Вопрос «скоуп»; про `team.md` — попросить аналитика |
   | `glossary.md` | Строки дописывает любой; структуру и чужие строки правит аналитик | — |
   | `datasets/PM-XX/` | Тестировщик, если он владелец или напарник рута | MR владельцу рута |
   | Объекты журнала `Q`, `A`, `D`, `R` | Шапку — хозяин: автор, кто принял, кто следит. «Ответ» дописывает любой, кто принёс ответ с источником. Статус `отвечен` ставит автор, владелец раздела, дежурный по знаниям или аналитик после созвона | Дописывать строки: «Подписчики», «Уточнения», «История». Ничего не удалять |
   | `_index.md`, `_map.svg`, `_map.html`, `journal/_renames.tsv` | Только CI (в соло — `kb.py after-merge`) | Не добавлять в свои коммиты; `kb.py index` — для просмотра |

5. Номера `Q`, `A`, `D`, `R` не придумывай: `python3 tools/kb.py new …` даёт временный ID, постоянный присваивает CI или `kb.py after-merge`. `_index.md` руками не правь.
6. Перед коммитом — `python3 tools/kb.py check`, ошибок 0. Коммит маленький, только свои файлы по именам (не `-A`); в сообщении — ID раздела и объектов журнала, последняя строка — `Скилл: kb-<имя>` (по ней руководитель видит, какие скиллы работают): `git commit -m "PM-04: исключения (Q-new-…)" -m "Скилл: kb-explore" -- <файлы>`. Ответ существует, только когда записан коммитом.
7. Персональные данные в репозиторий не попадают.

## Экономно и без потери точности

| Нужно | Команда | Вместо |
|---|---|---|
| Всё о шаге или системе | `python3 tools/kb.py context PM-XX` | Чтения карты, продукта, глоссария, сводок и шага по отдельности |
| Есть ли ответ или похожий вопрос | `python3 tools/kb.py similar "<формулировка>" "<синонимы>"` | Чтения всей базы и журнала. Совпадение слов — кандидат; дубль ли это, решаешь по смыслу |
| Что изменилось | `python3 tools/kb.py changes --since <хеш или дата>` | `git log -p` и чтения файлов целиком |
| Большой файл, CSV, Excel | `python3 tools/kb.py peek <файл>` | Чтения файла целиком. Дальше — считай и фильтруй скриптом, цитируй строки по номерам |

- Не читай для справки: исходники `tools/` (есть `python3 tools/kb.py --help`), `docs/` (написаны для людей), `.gitlab-ci.yml`, шаблоны `_template` (`kb.py new` сам создаёт файл по шаблону), другие скиллы (короткие правила для вопросов и рисков есть в текущем скилле; полный текст другого скилла — только когда человек переключился на него).
- Записывай командами `kb.py`, а не правкой файла руками: они сами держат формат и проверяют значения.

  | Что | Команда |
  |---|---|
  | Кто я, что у меня | `python3 tools/kb.py whoami` |
  | Факт в шаг или систему | `python3 tools/kb.py fact PM-XX "<Раздел>" "<текст>" "<источник и место>" <статус>` |
  | Новый вопрос, допущение, решение, риск — сразу заполненный | `python3 tools/kb.py new question <slug> тип=… раздел=… заголовок="…" "Контекст=…"` |
  | Новый шаг или система (аналитик) | `python3 tools/kb.py new step <slug> шаг="…" …`, `new system <slug> система="…"` |
  | Поле шапки (статус, тип…) | `python3 tools/kb.py set <ID> статус=…`; статус рута назад или через шаг — `--force "причина"` |
  | Строка в раздел (Подписчики, Уточнения, История, Ответ, Чем закрыто, Приёмка рута) | `python3 tools/kb.py append <ID> "<Раздел>" "<строка>"` |

  `<slug>` — короткое имя для ID латиницей через дефис, не имя человека: `istochnik-dolga` → `Q-new-istochnik-dolga`.
  Вывод со словом «ОШИБКА» — значение не принято: исправь и повтори. Таблицы и большие разделы правь в файле точечно.
- Материал больше 20 КБ: первый, кто его разбирает, кладёт рядом `<имя>.summary.md` — что в файле, структура, важные строки с номерами. Остальные читают выжимку. Факт всё равно ссылается на оригинал и строку.
- Правь точечно — раздел или строку. Файл целиком пиши, только когда создаёшь его.
- Вопросы человеку: независимые — одним сообщением, до 4, с вариантами ответа; зависящие от предыдущего ответа — по одному. Не спрашивай то, что есть в файлах.
- Отчёт человеку — до 7 строк: что записано (файлы, ID), что осталось открытым, следующий шаг. Не пересказывай то, что уже в файлах.
- Задача закончена, а следующая — другая: предложи новую сессию (`/clear`). Вся память — в файлах.

## Python

В скиллах — `python3`. Нет её (Windows) — `python` или `py -3`. Нужен Python 3.9+.

## Режим работы — поле `режим` в team.md

| | команда | соло |
|---|---|---|
| Через MR | Файлы, у которых один писатель и много читателей: шаги `PM-XX`, системы `SYS-XX`, `_map.md`, `core/`, `product.md`. Ветка на один раздел. Своё MR по своему файлу человек сливает сам после зелёного CI. Обязательное ревью только: первый рут новичка — аналитик; чужой файл — владелец; ядро — архитектор недели. Вопросы, заведённые во время разбора шага, едут в MR вместе с шагом | Прямо в основной ветке |
| Прямой коммит в основную ветку, без MR | Взятие и возврат рута (`take` / `release`); любые объекты журнала и строки в них (`new question/assumption/decision/risk`, `append`, `set` статуса своего объекта); дежурство (`kb-sync`); созвоны (`kb-interview`); `team.md` аналитиком. Перед коммитом — `git checkout <основная> && git pull --rebase`; коммитить только свои файлы по именам (`git add <файлы>`, не `-A`); работал в ветке — вернись в неё после | Так же, без переключения веток |
| Сгенерированные файлы `_index.md`, `_map.svg`, `_map.html`, `journal/_renames.tsv` | Коммитит только CI после каждого коммита в основную ветку. Люди их в коммиты не добавляют | После коммита — `python3 tools/kb.py after-merge`, затем коммит «kb: номера и сводки» |
| Номера Q, A, D, R | CI после каждого коммита в основную ветку. Ссылки на `X-new-…` из старых веток чинятся автоматически (`journal/_renames.tsv`) | `after-merge` |
| Чужой файл | MR владельцу | Обычно владелец — тот же человек, правь сам. Если человек сменил имя на другую роль и файл не его — ветка, коммит, вопрос «принимаете от имени владельца?», локальное слияние |
| Ревью архитектора | MR с ревьюером | Скажи, что человек сейчас отвечает как архитектор недели, и спроси подтверждение |

В соло человек может временно сменить `git config user.name` на другое имя из `team.md`, чтобы проверить другую роль. Тогда действуй по правам этого имени.

## Статусы рута

Порядок статусов проверяет `kb.py set`: только на следующий; назад или через статус — `--force "причина"`, причина пишется в «Приёмка рута».

| Переход | Кто и чем |
|---|---|
| Черновик → Готов к взятию | Аналитик, `kb-map` режим 3, после сверки структуры карты с бизнесом |
| → Разбор | `kb.py take` (`kb-take`). В `kb-explore`: статус «Готов к взятию» и ты владелец — поставь «Разбор»; другие статусы не трогай |
| → Сверка с бизнесом | Владелец в конце `kb-explore`, когда материалы исчерпаны и пробелы к бизнесу заведены вопросами (список готовности — в `kb-explore` §7). Статус значит «ждём сверки», в лимит рутов не считается — можно взять следующий |
| Сверка | Ведёт аналитик: `kb-interview` режим В «сверка рута PM-XX». Владелец с агентом готовит список «так ли вы работаете» по разделам шага и приходит слушателем. Итог — `materials/interviews/<дата>-sverka-PM-XX.md`, ответы в вопросы, владелец переносит через `kb-answer` |
| → Нарезка | `kb-slice` в начале: статус «Сверка с бизнесом» и файл сверки есть. Нет файла — нарезать нельзя |
| → Приёмка | `kb-slice` в конце |
| → Декомпозиты в работе | `kb-accept`, только если хотя бы у одного декомпозита нет открытых блокирующих вопросов без допущения; иначе рут остаётся в «Приёмке» с условиями |
| Назад | `kb.py set PM-XX статус=… --force "причина"`: архитектор при возврате с приёмки; владелец при переоткрытии после опровергнутого допущения |

Самоприёмка: владелец рута — архитектор недели. В команде принимает техлид потока или предыдущий архитектор по истории в `team.md`; в соло — допустимо с пометкой «самоприёмка» в «Приёмка рута».

## Тип вопроса → кто отвечает → канал

| Тип | Кто отвечает | Канал |
|---|---|---|
| понимание | Бизнес или материалы | Созвон или пакет для бизнеса (`kb-interview`, `kb-sync`); материалы — сам |
| бизнес-правило | Только бизнес | Созвон или пакет |
| факт о системе | Владелец системы в бизнесе или ИТ | Через аналитика |
| решение | Пул | `kb-decide`; в пакет для бизнеса не идёт |
| скоуп | Аналитик (структура карты) | `kb-map` режим 2 |

Противоречие → «бизнес-правило», если выбирает бизнес, иначе «решение». Кодом или данными закрываются только «понимание» и «факт о системе»; код расходится с регламентом — противоречие.

## Остановись и спроси человека

- Действие необратимо: миграция, деньги, внешний контракт, персональные данные.
- Нужно писать в файл другого владельца.
- Два источника противоречат друг другу.
- Нужно поменять структуру карты процессов.

## Обратная связь о скиллах

Правило скилла мешает, противоречит другому или непонятно — не обходи молча. Скажи человеку и предложи запись в `FEEDBACK.md`: скилл, шаг, что ожидалось, что мешает.
