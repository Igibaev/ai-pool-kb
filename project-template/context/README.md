# Контекст: как наполнять

Контекст описывает процесс бизнеса **как он есть сейчас**, а не как хотим. Желаемое появляется в спеках.

## Кто что делает

| Кто | Что делает |
|---|---|
| Аналитик | Ведёт созвоны с бизнесом (`kb-interview`) — вместе с менеджером, если роль бизнеса идёт через него. Разработчики бизнесу не звонят. Создаёт структуру: шаги и системы командами `kb.py new step` / `new system` (`kb-map`). Готовит шаги к взятию: зачем, вход и выход, участники, материалы и роль в бизнесе, приоритет — и останавливается. Владеет структурой: делит, объединяет, добавляет шаги. Ведёт `product.md`, `_map.md`, `team.md`, структуру `glossary.md`; переносит ответы на вопросы `ROOT` и рутов без владельца. Ревьюер первого рута у новичка |
| Владелец рута | Берёт рут сам (`kb-take`). Разбирает свой шаг от и до, задаёт вопросы, принимает допущения, ставит «Сверка с бизнесом», готовит список для сверки, переносит ответы (`kb-answer`), режет рут на декомпозиты |
| Напарник (`людей: 2`) | Пишет в разделы шага, о которых договорился с владельцем; статус и нарезку не ведёт |
| Техлид потока | Берёт `PM-00` (`take PM-00`), ведёт `core/`. Нет техлида — архитектор недели |
| Разработчики | Разбирают скрипты, код и выгрузки систем: «Как сейчас», «Правила», «Идентификаторы», «Данные» |
| Тестировщики | Разбирают реальные файлы и данные: «Объём и время», «Исключения», золотой датасет `datasets/PM-XX/` — пишут туда сами, если владелец или напарник рута, иначе MR владельцу |
| Веб-разработчики | Разбирают, что люди видят в текущих инструментах, когда принимают решение |
| Любой из пула | Дописывает строки в `glossary.md` (структуру и чужие строки — аналитик) |
| Бизнес | Сверяет структуру карты, затем каждый рут: «вы правда так работаете?» (`kb-interview` режим В) |
| Архитектор недели | Принимает рут (`kb-accept`): полнота, нарезка, пересечения; пишет «Приёмка рута» и ставит статус — названное исключение из «один файл — один писатель» |

## Правила

1. Факт — только из материалов: скрипт, файл, выгрузка, код, интервью, ответ в журнале. Из опыта — вопросы, а не факты.
2. Формат факта: `текст факта (источник, статус)`.
   - `подтверждено` — источник проверяемый или бизнес подтвердил письменно;
   - `допущение A-NNN` — решили сами, ждём подтверждения;
   - `противоречие` — источники расходятся, заведён вопрос (определение — `AGENTS.md`, правило 3);
   - `оценка` — цифра или утверждение со слов человека, который сам не уверен («примерно 200 в день»). Нормально для новой идеи; проверяется позже.
3. Структуру шага не меняют молча. Нашли, что шаг надо разделить или объединить, — вопрос в журнал, решает аналитик.
4. Роли, а не имена: «бухгалтер», а не «Айгерим».
5. Объёмы, частоту и время — числами.

## Готовность шага к взятию

Аналитик ставит «Готов к взятию», когда в шаге есть всё, чтобы чужой человек начал разбор без аналитика:

- [ ] **Зачем** — одна-две фразы;
- [ ] **Вход и выход** — по строке «Вход: …», «Выход: …»;
- [ ] **Участники** — хотя бы одна роль;
- [ ] **Материалы и контакты** — хотя бы один файл из `materials/` с пояснением, что в нём по шагу, и «Кто отвечает в бизнесе: <роль>» (через кого ходить — `team.md`);
- [ ] **приоритет** в шапке — числом;
- [ ] **людей** в шапке — 1 или 2; `ready-check` даёт только подсказку, решает аналитик;
- [ ] структура карты сверена с бизнесом — до этого шаги остаются в «Черновике».

Проверка: `python3 tools/kb.py ready-check PM-XX`. Остальное — «Как сейчас», «Объём», «Правила», «Исключения», «Идентификаторы», «Данные» — заполняет владелец. Аналитик на этом шаге останавливается: 30–60 минут на шаг.

## Путь рута

Статусы и кто их ставит — таблица «Статусы рута» в `AGENTS.md`. Коротко: аналитик → «Готов к взятию»; `take` → «Разбор»; владелец в конце разбора → «Сверка с бизнесом» (в лимит не считается); аналитик проводит сверку (`kb-interview` режим В, файл `materials/interviews/<дата>-sverka-PM-XX.md`); `kb-slice` → «Нарезка» → «Приёмка»; `kb-accept` → «Декомпозиты в работе» или возврат с причиной.

## Если владельцу не хватает опыта анализа

Разбор — навык, который у разработчиков бывает разным. Пробелы не закрывают догадками.

1. **Агент ведёт.** `kb-explore` видит пустые разделы (`kb.py context` показывает «Заполненность»), объясняет, что в каждом нужно и где это обычно искать, и задаёт вопросы по направлениям из `docs/thinking.md`.
2. **Материалов не хватает — вопрос, а не звонок.** Владелец оформляет пробел вопросом (`kb-ask`) языком бизнеса; тип и кто ответит — таблица «Тип вопроса» в `AGENTS.md`. С бизнесом говорит аналитик: собирает вопросы пула к одной роли в один созвон (`kb-interview`), ответы пишет в вопросы, а владелец переносит их в шаг (`kb-answer`). Так бизнес отвечает раз в день, а не каждому разработчику.
3. **Аналитик — ревьюер первого рута** нового человека: смотрит MR, где факты похожи на догадки. Это одно из трёх обязательных ревью (ещё — чужой файл и ядро); своё MR по своему файлу человек сливает сам после зелёного CI.
4. **Созвон прошёл, а ключевые разделы пусты** — аналитик идёт в пару. Рут не забирают: владелец остаётся владельцем.
5. **Сверка рута** — не разработчик защищает свою работу, а бизнес проверяет утверждения: владелец с агентом готовит список «так ли вы работаете» по разделам шага, аналитик ведёт созвон, владелец слушает.
6. **Проверка ловит формальные ошибки:** факт без источника или статуса не пройдёт `kb.py check`.

## Сколько карт процессов

**Одна карта — один сквозной процесс главного объекта.** Почти всегда у продукта одна карта: `context/process/_map.md`.

| Ситуация | Что делаем |
|---|---|
| Новая функциональность | Не новая карта, а декомпозиты внутри шагов существующей карты |
| Шаг слишком большой, внутри свой маршрут | Аналитик делит шаг на несколько шагов той же карты |
| У продукта несколько главных объектов с независимым жизненным циклом (например, внесудебное взыскание и судебное) | Несколько карт: `context/process/<процесс>/_map.md`, ID шагов `PM-XX` сквозные по продукту, связи между картами — в разделе «Шаги» каждой карты |

Признак, что нужна вторая карта: у объекта свои состояния от появления до закрытия, и он может жить без первого процесса.

## Совместная работа

С контекстом одновременно работает весь пул, поэтому у каждого файла один писатель.

Кто какой файл пишет и что могут остальные — таблица в правиле 4 `AGENTS.md`; что идёт через MR, а что прямым коммитом — таблица «Режим работы» там же. Коротко: шаги, системы, `_map.md`, `core/`, `product.md` — через MR; журнал, взятие рутов, дежурство, созвоны, `team.md` — прямым коммитом; `_index.md`, `_map.svg`, `_map.html` коммитит только CI.

- Перед работой — `git pull --rebase`, если есть remote. Ветка — на один раздел, живёт часы.
- Перед отправкой — `python3 tools/kb.py check`.
- В сообщении коммита — ID раздела и ID вопросов или допущений, которых коснулась правка, последней строкой — скилл: `PM-04: исключения по выпискам (Q-021)` + `Скилл: kb-explore`.

## Готовность карты

Карта готова для первых декомпозитов, когда по ней можно ответить:
- что движется по процессу (главный объект);
- кто и в чём с ним работает на каждом шаге;
- сколько этого и как часто;
- где теряются время и деньги;
- какие данные где рождаются и кто источник правды.
